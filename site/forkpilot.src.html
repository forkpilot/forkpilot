Find what changed before you fly.

ForkPilot flies a battery of SITL scenarios on your last good commit and on the new one. A deterministic oracle decides whether flight behaviour changed. ForkPilot then finds the commit that changed it and tries fix candidates. Simulation does not replace flight tests. It narrows down what to test.

Problem

A fork changes behaviour quietly

A fork merges upstream or adds its own commits, and some flight behaviour changes. It is hard to see in a large diff, and it may only show up in a flight test, where it is slow and expensive to find.

Merges hide behaviour changes

Controller, EKF and driver changes can shift flight behaviour without any build error or failing unit test.

Flight tests should confirm, not search

Pilot, field, weather and crash risk make flights slow and costly. They are the wrong tool for finding which commit broke something.

SITL exists, scenarios do not

Writing scenarios, defining metrics and wiring them to a pipeline is a separate infrastructure project.

Upstream CI tests upstream

It does not fly your airframe parameters or your custom code. Your fork needs its own checks.

How it works

Fly both commits. Let rules decide.

ForkPilot builds your good and bad commits, flies the same scenarios on both, and compares the results against a baseline from the good side. Everything that decides is deterministic. A language model is optional and only proposes.

deterministic: decideslanguage model: proposes only
The AI never decides.

A deterministic oracle decides every verdict. A language model may explain the evidence and propose a patch. Every claim it makes is either quoted from the evidence or checked by flying, and a candidate fix is judged by the same oracle. A candidate that passes is still only a candidate: read the diff and fly it.

PASSno rule broken, metrics inside the baseline band
DRIFTno rule broken, but a metric's mean left the band: mean ± max(3·sd, 10% of |mean|, 0.05)
FAILa rule in the scenario's expect block is broken, or the scenario did not complete
Stage 1 · deterministic

Detect

The full battery runs on the good commit (baseline, cached) and on the bad one. The oracle gives a verdict per scenario. ArduPilot's own autotest (about 400 tests) can run as a first screen: each drift is then confirmed on fresh reruns of both sides.

Stage 2 · deterministic

Triage

Each non-PASS scenario is rerun and classified: consistent, intermittent, flaky, preexisting or infra. Only real, repeatable changes go on to bisect.

Stages 3-4 · deterministic

Bisect and evidence

A binary search finds the first commit that shows the same symptom (same scenario, metric and direction). It skips commits that do not build and reports them. The result is written to evidence.md: oracle findings, first divergence in telemetry, culprit diff.

Stages 5-6 · optional language model

Explain and fix

An explanation is written from evidence.md only, and quotes not found there are marked unverified. Fix candidates (a known upstream fix, a plain revert, model-written edits) are built and flown, and the oracle judges each one.

DRIFT

ArduPlane and QuadPlane

Scenarios name their vehicle and frame. Six starter scenarios cover plane and QuadPlane missions, modes, a battery failsafe and an RC loss. Plane metrics include airspeed, TECS height, cross-track, transition time, VTOL assist and touchdown point.

Plane SITL is close to deterministic. Each metric falls into a few discrete values, so floors keep a narrow baseline from flagging the same binary.

For your fork

Built for teams that maintain their own fork

Everything runs on your machine. ForkPilot opens no network connection except to an LLM server, and only if you ask for one. A first investigation on your own fork takes about 15 minutes of your time, plus machine time for the first builds.

Your scenarios

A scenario is one YAML file: steps, parameters and expect rules. The lint command checks them before anything flies, and a scenario directory is added to the shipped ones. A regression in something you changed is found only if a scenario flies it.

Replay a field report

The fromlog command turns a flight log (DataFlash .bin, or a lower-fidelity .tlog) into a scenario with the same stick inputs, mode changes and mission. Fly it against any two builds of your fork. Read the generated YAML before you trust it.

Copter, Plane, QuadPlane

ArduCopter, ArduPlane and QuadPlane scenarios fly in SITL, each with its frame's default parameters from the commit under test. PX4 SITL support: in progress.

Check your setup first

The doctor command checks Python, build tools, submodules, a clean tree, both commits, disk, cores and RAM. Every line that is not OK says what to do. A smoke test builds the SITL binary and flies one scenario.

Local model backend

The explain and fix stages can use any OpenAI-compatible endpoint (vLLM, llama.cpp server, Ollama), so nothing leaves your site. A hosted API backend is also available. Both stages are optional.

A report that opens anywhere

The report command writes one report.html with no script and no requests, in light and dark. It opens on an air-gapped network. It holds the verdict summary, telemetry and baseline-band plots, bisect trail, culprit diff, explanation and fix candidates.

Limits

What it does not do

It does not replace flight tests

Simulation results narrow down what to test. Passing in SITL does not mean the aircraft is safe to fly. ForkPilot finds regressions before flight testing, not instead of it.

It finds what a scenario flies

A battery that does not fly a behaviour cannot see a change in it. Most misses on the dev cases are of this kind. Add scenarios for the code you changed.

Hits so far are post-hoc

The scenario hits on dev cases come from scenarios written after the cases were studied. The blind holdout is the test of how often a fixed battery catches an unseen bug.

A merge is one bisect step

If your fork merges upstream, the culprit can be the merge commit. ForkPilot cannot name the upstream commit inside it. Investigate the merged branch separately.

Candidate fixes are candidates

A candidate that makes the oracle pass has passed simulated scenarios only. Read the diff and fly it.

Vehicle support

ArduCopter, ArduPlane and QuadPlane SITL are supported. PX4 SITL support: in progress.
